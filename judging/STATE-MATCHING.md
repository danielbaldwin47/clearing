All four source stills are retained unchanged with checksums. Compare only their content crops, never descriptions or fresh downloads. Crops remove chrome, branding, and operating-system controls. Task labels stay because deleting the wrong content is a material usability failure.

- `shots-ss.jpg`: strongest and largest saved visual reference, scanned user directory with ranked categories and staged-delete affordance. Suitable for shared visual foundation and overview.
- `intro-ss1.png`: same category, older visual treatment, selected user subtree with ranked contents and staged-delete affordance. Suitable for breadth validation after strongest reference.
- `intro-ss2.png`: volume root overview including free and purgeable space. Suitable for whole-bar overview breadth, not as an exact directory-size target.
- `intro-ss3.png`: volume scan picker. This is not a scanned-directory map, a drilled directory, or a confirmation dialog. Retain as reference evidence; never mislabel it as one of the requested states.
- Installed diskonaut: actual overview, drilled `ssd-story/Caches`, and pending deletion of `ssd-story/Caches/Browser/Media Cache/video-buffer.bin` captured on the exact same fixture and terminal as the candidate. These are the live behavioral-state bar.

The canonical content canvas is 1260×880 pixels. Terminal originals are 140 columns × 44 rows, DejaVu Sans Mono 11, fully headless, truecolour enabled. The extra one-pixel kitty raster edge is cropped. Saved references are cropped at fixed coordinates and proportionally fitted with their own background colour; no aspect-ratio stretching, inserted content, selective contrast changes, or invented controls.

First calibration observed an honest initial implementation preferred for its labeled rectangles and action hints. The referee recorded this loss before investigating: no product win and no calibration success. This is evidence that the original negative control was already functionally complete enough to compete on task clarity. A stronger reference and an explicitly unfinished builder wireframe are needed to test whether judges can detect a real quality deficit. The control must remain an actual rendered builder artifact, never a sabotaged screenshot.

## Piece boundaries

Foundation judging uses only map plus legend crops. It assesses shared hue relationships, text contrast and weight, and proportional area encoding; path display, top summary, action hints and confirmation wording are excluded. Overview judging uses complete overview captures to assess information hierarchy, ability to locate a cleanup target and action discovery. Navigation judging uses the same drilled directory in both live interfaces. Deletion judging uses the same file and pending confirmation state in both live interfaces. Whole judging includes the complete state sequence and both applicable bars.

Fingerprint dependencies are explicit after the builder split modules: foundation uses `src/theme.rs` and `src/ui/foundation.rs`; overview additionally uses `src/ui/view.rs`; navigation additionally includes `src/ui.rs`; deletion includes the shared/view modules plus `src/ui/confirm.rs`; whole includes all UI, main and scan sources. A referee watchdog compares all won-piece fingerprints every two seconds and clears a win immediately if a dependency changes.

## First-round state audits

The first complete-overview verdict was not counted because the reference crop removed application breadcrumbs and back/forward controls while removing platform furniture. The repeated packet keeps those application controls and masks only the platform window buttons. Foundation map-only judging is unaffected because its declared scope deliberately excludes navigation chrome for both entries.

The first navigation verdict was not counted because the two actual just-drilled defaults differed: the candidate automatically selected Browser, while the installed live bar left nothing selected. The repeated packet explicitly selects Browser in both. This removes the selection mismatch as an explanation for an easy first-round win.

The delete bar's grey main pane was verified by an independent recapture: the pending-confirmation body is pixel-identical. The file is the only child, and the large grey rectangle is its native selected appearance, not a rendering failure. The captured deletion state won after audit; that historical win was immediately invalidated for authorized new deletion/cancellation behavior. It will need a new fresh verdict on the final build.

The fixture independently contains two regular leaf files below Browser and two descendant directories. The candidate's “2 files” and live bar's “4 descendants” therefore describe the same tree accurately. A critic's suspicion about this count is retained as taste evidence, not converted into a false implementation bug.
